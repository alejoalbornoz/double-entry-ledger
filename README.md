# Double-Entry Ledger

A double-entry ledger system built with Spring Boot, focused on the core problems a real financial backend has to solve: **transactional consistency, idempotency, and safe concurrent access to shared state.**

This is not a banking app. It doesn't have user auth, KYC, or a UI. It's a focused implementation of a ledger engine — the kind of component that sits underneath a product like Mercado Pago or Ualá — with the emphasis on correctness under concurrency, not on feature breadth.

## Why this project

Most portfolio CRUD projects don't force you to deal with the problems that actually separate a mid-level backend engineer from a senior one: what happens when two requests modify the same row at the same time? What happens if a transfer is retried by a flaky client? How do you *prove*, not just assume, that money is never created or destroyed?

This project is an attempt to actually answer those questions with tests, not just with claims.

## Tech stack

- **Java 17 / Spring Boot 4.1**
- **PostgreSQL 16** — chosen over MySQL for stronger support of serializable transactions and `CHECK` constraints, which let invariants (like non-negative balances) be enforced at the database level, not just in application code.
- **Hibernate / JPA** — with `ddl-auto: validate`. The schema is never generated by Hibernate; it's owned entirely by Flyway migrations, and Hibernate only validates that entities match what's actually in the database.
- **Flyway** — versioned schema migrations.
- **Spring Retry** — automatic retry with exponential backoff on optimistic locking conflicts.
- **Spring Scheduling** — hourly reconciliation job.
- **Jakarta Bean Validation (Hibernate Validator)** — request and header validation.
- **Docker Compose** — Postgres, Redis, and pgAdmin for local development.
- **Lombok** — used selectively (`@Getter`/`@Setter`, not `@Data`) to avoid the classic JPA pitfalls around `equals()`/`hashCode()`/`toString()` on lazy-loaded relationships.

## Domain model

```
Account         — holds a cached balance, protected by @Version (optimistic locking)
Transaction     — a single business operation (TRANSFER, DEPOSIT, WITHDRAWAL)
LedgerEntry     — immutable accounting record: DEBIT and/or CREDIT tied to a Transaction
IdempotencyKey  — caches the response for a given idempotency key
```

**Core invariant:** every `Account.balance` must be fully explained by the sum of its `LedgerEntry` records — nothing else is allowed to change a balance. For internal transfers specifically, `sum(DEBIT entries) == sum(CREDIT entries)` per `Transaction` (money doesn't appear or disappear, it moves). For deposits and withdrawals — money crossing the system's boundary — a `Transaction` produces a single `LedgerEntry`, since there's no internal counterpart account. Both cases are enforced by `TransferService` / `AccountService` and verified by `TransferServiceIntegrationTest` and, system-wide, by the reconciliation job described below.

`Account.balance` must never be set directly (`account.setBalance(x)`) outside of ledger-backed operations. Doing so silently breaks the core invariant — see the "What reconciliation actually caught" section for a real example of this happening in this project's own tests.

`LedgerEntry` has no setters — it's intentionally immutable. A ledger entry is a historical accounting record; once written, it should never be mutated. If application code ever needs to "fix" a `LedgerEntry`, that's a sign the correction should be a new, compensating transaction — not a mutation.

## Architectural decision: monolith, not microservices

Early on, this project could have been split into `account-service` and `ledger-service` to "look more like production systems." That was deliberately rejected.

A transfer requires debiting one account and crediting another **atomically** — in a single database transaction. Splitting that across two services would mean giving up ACID guarantees and reaching for a Saga pattern with compensating transactions to handle partial failures. That's real distributed-systems complexity, and it would have been **self-inflicted**: the domain doesn't require it, since both accounts live in the same bounded context and the same database.

The system is a modular monolith instead: clear package boundaries (`domain`, `service`, `repository`, `controller`) that make it straightforward to split off a genuinely independent concern — like notifications or reporting — later, via an outbox/event pattern, without having paid the tax of distributed transactions on the one part of the system where consistency matters most: money movement.

## Concurrency: the core of this project

The most interesting engineering problem here is: **what happens when multiple transfers hit the same account at the same time?**

### Locking strategy

`Account.version` is an optimistic lock (`@Version`). Two concurrent transfers that both read the same account version will conflict: only one `UPDATE ... WHERE id = ? AND version = ?` succeeds, the other affects zero rows and Hibernate throws `ObjectOptimisticLockingFailureException`.

Optimistic locking was chosen over pessimistic (`SELECT ... FOR UPDATE`) because transfers are short-lived operations and conflicts, while they happen, are not the common case — pessimistic locking would serialize all access to a "hot" account even when there's no actual conflict, hurting throughput unnecessarily.

To avoid deadlocks on transfers between the same two accounts in opposite directions (A→B and B→A executing concurrently), both accounts are always locked in a deterministic order (ascending UUID), so every thread acquires locks in the same sequence.

### The problem with just using `@Version`

Optimistic locking guarantees the balance is never corrupted — but on its own, it also means **legitimate transfers get rejected** under contention, with no automatic recovery. That's a real usability problem for a financial system: a user's valid transfer failing just because another transfer happened to touch the same account at the same instant is not acceptable.

### Solution: retry with exponential backoff

`TransferRetryService` wraps `TransferService` with `@Retryable`, retrying on `OptimisticLockingFailureException` with exponential backoff. This was tuned empirically, not guessed — `TransferConcurrencyTest` fires 10 threads at the same source account simultaneously and measures how many succeed:

| Configuration | Successful | Failed |
|---|---|---|
| No retry | 1 / 10 | 9 / 10 |
| Retry, `maxAttempts=5`, backoff 50ms (no cap) | 5 / 10 | 5 / 10 |
| Retry, `maxAttempts=10`, backoff 100ms × 2, capped at 2000ms | **10 / 10** | 0 / 10 |

In every configuration, the account's final balance was verified to be exactly correct — optimistic locking never once allowed a corrupted balance, even when it rejected valid transfers. What retry tuning fixed was availability under contention, not correctness.

This is the trade-off worth naming explicitly: retry count and backoff aren't free — too few attempts and legitimate operations fail under load; too many, or too aggressive a backoff, and you risk amplifying contention or making the caller wait unacceptably long. The numbers above reflect one specific contention scenario (10 threads on 1 account); a production system would need load-representative testing to tune this properly, not a fixed guess.

## Idempotency

Clients are required to send an `Idempotency-Key` header on every transfer, deposit, and withdrawal. This protects against the classic "client retries a request that actually succeeded, but the response was lost" scenario — without it, a retried transfer would move money twice.

**The actual safety mechanism is a database constraint, not an application-level check.** `transactions.idempotency_key` has a `UNIQUE` constraint, and the `Transaction` row is inserted **inside the same database transaction** that moves funds. If two requests with the same key arrive concurrently, both try to insert a row with that key — Postgres allows exactly one to succeed, and the other fails with a constraint violation *before* any balance is touched. There's no race window between "check if this key exists" and "act on it," because there's no separate check: the insert itself is the check.

A separate `IdempotencyKey` table caches the serialized response per key + request-payload hash, purely so a retrying client gets back the exact same response instead of having to reconstruct it. Reusing a key with a *different* payload is treated as a client bug (or a stolen/colliding key) and rejected with `409 Conflict`, not silently accepted.

Verified manually end-to-end:

| Step | Result |
|---|---|
| First request with a new key | `201 Created`, transfer executes |
| Identical retry, same key + same payload | `200 OK`, cached response, balance unchanged |
| Same key, different payload (`amount` changed) | `409 Conflict` |

## Reconciliation

A scheduled job (hourly, plus a manual `GET /api/admin/reconciliation` endpoint) recomputes every account's balance from scratch by summing its `LedgerEntry` records, and compares that against the cached `Account.balance`. It's intentionally **read-only** — it reports mismatches, it never "fixes" them automatically. Auto-correcting a financial discrepancy without a human looking at it first is how you turn a bug into a cover-up.

### What reconciliation actually caught

This isn't a hypothetical. While building this feature, running it for the first time against the database used by the integration and concurrency tests returned **11 accounts with discrepancies**, all off by exactly `500` or `1000`:

```json
{ "accountId": "80d224f8-...", "cachedBalance": 700.00,  "computedBalance": -300.00 }
{ "accountId": "bdcc594e-...", "cachedBalance": 750.00,  "computedBalance": -250.00 }
{ "accountId": "73b8fad1-...", "cachedBalance": 500.00,  "computedBalance": -500.00 }
```

The round, repeated amounts were the tell. The integration and concurrency tests were seeding test accounts by calling `account.setBalance(BigDecimal)` directly to give them starting funds — exactly the pattern the core invariant forbids. Those accounts had a balance with no `LedgerEntry` behind it at all.

The fix was twofold: add `AccountService.deposit()` — the only sanctioned way to fund an account, always backed by a real `LedgerEntry` — and update both tests to use it instead of touching `balance` directly. After resetting the database and re-running everything, reconciliation reported `0` discrepancies.

The forced-failure test that validates the detector itself: fund an account through the API, confirm `0` discrepancies, then bypass the application entirely with a raw `UPDATE accounts SET balance = balance + 1000 WHERE id = ...` in the database. Reconciliation immediately flagged that exact account with a `1000` mismatch. Reverting the manual `UPDATE` brought it back to `0`.

## Testing strategy

- `TransferServiceIntegrationTest` — runs a real transfer against a real Postgres instance (via Docker Compose, not mocks) and asserts: final balances, exactly 2 `LedgerEntry` records, and that debits equal credits.
- `TransferConcurrencyTest` — fires concurrent transfers from the same account and asserts the final balance is exactly what it should be, regardless of how many individual transfer attempts failed and were retried.

Both are integration tests against a live database on purpose. The whole point of this project is proving behavior under real transactional and concurrency semantics — an in-memory or mocked database wouldn't exercise the actual locking behavior being tested. (Testcontainers is a planned follow-up, to remove the manual dependency on `docker compose up` before running tests.)

## Known trade-offs and things a production system would still need

- **No Testcontainers yet** — tests currently depend on a manually-started Docker Compose stack rather than spinning up an isolated, disposable database per test run.
- **No pessimistic-locking fallback** — under sustained, very high contention on a single account, retry-with-backoff has diminishing returns; a production system might switch to pessimistic locking for known "hot" accounts, or shard load differently.
- **Auth is intentionally minimal** — this project is scoped to the ledger engine itself, not to user management. A `User` entity and basic JWT-based auth may be added as a thin layer on top, but it's explicitly not the focus.
- **Reconciliation is read-only by design** — a real production system would still need an operational runbook for what a human does when a discrepancy fires, not just a log line.
